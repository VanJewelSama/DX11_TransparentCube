### 1.1 当前功能总览

当前一帧的主流程：

```text
Shadow Pass（光源正交相机 → ShadowMap）
    ↓
Reflection Pass（镜像相机 → Reflection RT，排除镜面自身）
    ↓
主 SceneColor Pass
    ├─ Opaque：CubeA（颜色 + 法线贴图）/ 地面 / 镜面
    └─ Translucent：CubeB（写 stencil=1）
    ↓
PostProcess（FXAA → Copy / Grayscale / MaskedDarken）
    ↓
Present
```

| 模块 | 当前实现 |
|---|---|
| 窗口 / 输入 | Win32 窗口、消息泵、键鼠采样、右键视角模式 |
| 相机 | PCM 模式：FreeCamera / FixedCamera，1/2 切换 |
| 场景 | CubeA（贴图 + 法线贴图、自转）、地面、CubeB（img_cube_2 半透明）、平面镜、CubeC（Toon 风格化） |

运行方式：

- VS 里 F5：工作目录通常是项目目录，直接读项目中的 `shaders/`、`assets/`；
- 双击输出目录的 exe：构建后 `shaders/`、`assets/` 已复制到 exe 旁边。

当前已知限制：

- 后处理为 LDR、单 Pass 链；没有 HDR / Tonemap / Bloom。
- 法线贴图目前只用于 CubeA；地面和 CubeB 使用 1×1 平坦法线。法线贴图尚未切换为
  BC5 压缩，也没有可视化的强度/开关 UI。
- 贴图已使用 GPU GenerateMips + 8× anisotropic filtering；顶部掠射角闪烁已缓解。
- 未来可能统一改为“assets 只读 DDS”，PNG/JPG 在导入时用离线工具生成 mips/BC7（见 §6.5）。
- 未做 sRGB 线性工作流。
- 已实现 FXAA（数字键 0），但还没有 MSAA / SSAA；FXAA 会略微软化画面，
  而且 **不能解决纹理 minification 造成的闪烁**。
- 平面镜没有斜近裁剪面、没有递归反射；场景里镜面后方暂时没有其它物体。
- 透明排序是逐物体排序，不处理互相穿插的透明物。
- 点光源不投阴影（点光阴影需 cubemap + 6 Pass）；衰减为教学近似，非物理光度单位。
- 模板功能依赖 `D24_UNORM_S8_UINT`；若改成纯 `D32_FLOAT` 会失效。

## 2. 与初始计划（01 文档 §3）的结构差异

### 2.1 分层：从"平铺小程序"到四模块目录

- 计划：`Material / SceneObject / Scene / Camera` 几个结构体平铺。
- 实际：按 UE 模块思想分为 **Core / RHI / Renderer / Scene** 四个目录。
  RHI 是对 D3D11 API 的薄封装（≈ FD3D11DynamicRHI），Renderer 只通过它接触 DX API。

### 2.2 场景对象：SceneObject 结构体 → Actor 类层级

- 计划：`SceneObject { transform, mesh, material }` 简单结构体。
- 实际（经两轮设计讨论定型）：
  - `Actor` 基类只持有"存在性"：Transform（Location/Rotation/Scale）+ 虚 `Tick`，**不含外观数据**；
  - `StaticMeshActor : Actor` 持有外观（`Mesh*` + `MaterialData`）+ 轻量行为字段
    （`RotationRate`，Tick 里判空后自转）。`Material` 集中保存基础色、粗糙度、
    高光强度和半透明标记，对应 UE 材质实例参数的最小版。
- 关键决策：自转等行为**不进基类**（贴合 UE 思想——UE 中网格在 StaticMeshComponent、
  旋转在 RotatingMovementComponent，本 demo 不实现组件系统，用浅类层级+成员字段表达同样的分离，
  代价是每个对象多占少量内存，可接受）。

### 2.3 Scene：数据容器 → 管理结构

- 计划：`Scene { vector<SceneObject>, camera, light }` 被动数据。
- 实际：
  - `SpawnActor<T>()` 工厂（≈ UWorld::SpawnActor）：Scene 以 `unique_ptr` 拥有所有 Actor，外部拿裸指针；
  - `Scene::Tick(dt, input)` 是每帧逻辑刷新的统一发起者（相机 → 所有 Actor::Tick → PCM 缓存）；
  - 渲染侧只读访问（`GetActors()` const）。

### 2.4 相机：硬编码矩阵 → PlayerCameraManager 模式

- 计划：`Camera { position, target, up, fov... GetViewMatrix/GetProjMatrix }`，渲染直接用它。
- 实际（PCM 模式）：
  - `CameraViewInfo` ≈ FMinimalViewInfo：纯视角数据 + View/Proj 派生函数；
  - `ICamera` 接口：`GetCameraView()`（PCM 每帧拉参数）/ `Tick()` / `BindTo()`（相机自己与 PCM 绑定）；
  - `CameraManager`：只持有 ViewTarget 指针 + **当前帧/上一帧两份缓存**（`GetPrevViewInfo()` 留待相机过渡插值）；
  - **渲染流程只从 PCM 缓存取视角，不接触任何具体相机**；
  - 已实现 FreeCamera（右键+WASD 飞行）/ FixedCamera（复刻 M2 机位）两种类型，1/2 切换验证机制。

### 2.5 主循环：显式区分逻辑刷新 / 渲染刷新

```cpp
scene.Tick(dt, input);      // ① 逻辑刷新：可改状态（≈ 游戏线程侧）
renderer.Render(scene);     // ② 渲染刷新：const Scene& 只读（≈ 渲染线程契约）
```

单线程下顺序执行，用 `const Scene&` 把"渲染不得改逻辑状态"的契约写进类型系统——
这是 UE 游戏/渲染线程分离的思想内核，单线程下零成本表达。

DemoMain 把模块对象收拢到匿名命名空间的全局变量（`g_window / g_input / g_renderer / g_scene`），
并把职责拆成 `InitializeDemo()`（窗口/设备/场景初始化）、`BuildScene()`（SpawnActor 摆放内容）、
`Update()`（每帧逻辑刷新）和 `main()`（COM 检查 + 主循环）。全局对象按声明顺序构造、逆序析构；
`g_com` 声明在最前面，因此最后析构，保证 Scene 里的 WIC/D3D 资源先释放再 `CoUninitialize`。

### 2.6 渲染收集：筛选可渲染物

- 计划：直接遍历 objects 全画。
- 实际：`dynamic_cast<const StaticMeshActor*>` 从 Actor 列表筛出可视对象
  （≈ FScene 收集 primitive 的最小版；未来光源/触发器等非可视 Actor 自然被跳过）。
  曾讨论"基类加 renderable 标记"方案，结论：标记与类型是两份需手动同步的信息，
  dynamic_cast 让类型本身成为标签，本规模下开销为零。

### 2.7 输入模块（计划外新增）

`Core/Input`：每帧采样键盘 256 键（按住/边沿两级查询）+ 右键视角模式
（隐藏光标、锁定客户区中心、上报相对位移），替代了早期 `GetAsyncKeyState` 散装调用。

### 2.8 调试设施：实体/线框双光栅化状态

两套 `ID3D11RasterizerState`（实体 CULL_BACK / 线框 CULL_NONE+WIREFRAME），Tab 切换。
线框不剔除是为了画出全部 12 条边，便于检查网格拓扑。

### 2.9 M4 光照与材质

- **顶点**：`Position + Normal`（M5 再加 UV）。立方体改成 24 顶点——同一角点在相邻三面上的
  法线不同，8 个共享顶点无法同时携带三个法线；每个面复制 4 个角点，索引仍是 36。
- **材质**：`Scene/Material.h` 集中保存 `BaseColor / TintStrength / Roughness /
  SpecularIntensity / bIsTransparent`（M5 再加 `TexturePtr`），
  `StaticMeshActor` 持有 `MaterialData`；着色器只接收参数，不依赖具体材质类型。
  `TintStrength` 控制贴图颜色与 BaseColor 的 RGB 混合程度（0=纯贴图，1=完全染色），
  Alpha 始终来自 `BaseColor.a`。
- **光源**：`Scene/Light.h` 的 `DirectionalLight` 由 `Scene` 持有，`Renderer` 只读；
  方向存"表面 → 光源"的 L，与 shader 公式一致。
- **常量缓冲分两级**：
  - `PerFrameCB`（b0）：`ViewProj / CameraPosition / LightDirection / LightColor / AmbientColor`，每帧上传一次；
  - `PerObjectCB`（b1）：`World / NormalMatrix / BaseColor / MaterialParams`，每个 DrawCall 前上传。
- **法线矩阵**：CPU 端算世界矩阵的逆转置 `(World^-1)^T`，避免非均匀缩放把法线拉歪；
  shader 里用 `mul((float3x3)gNormalMatrix, n)` 变换到世界空间。
- **光照模型**：Lambert 漫反射 + Blinn-Phong 高光（半程向量 `H = normalize(L + V)`）+
  恒定环境光。`roughness` 被映射成 Blinn-Phong 的高光指数，只是教学近似，不是 PBR。
- **已知视觉限制**：立方体每个面法线恒定，高光在单个面上近似均匀，不会像球面那样形成圆形光点；
  指数越大，整面高光越容易直接消失。这是几何性质，不是光照公式写错。
  M11 在 CubeA 上加入法线贴图后，倒角/凹槽处会出现由细节法线驱动的非均匀高光（见 §2.18）。

### 2.10 M5 贴图管线

- **顶点**：M5 时是 `Position + Normal + UV`；M11 扩展为
  `Position + Normal + Tangent + Bitangent + UV`（见 §2.18）。
  输入布局用 `offsetof(Vertex, ...)` 定位，避免手写偏移。
- **UV 生成**：立方体每个面给一个 `Up` 参考方向，用面内切线基计算：
  `Right = cross(Normal, Up)`，`u = dot(P, Right) + 0.5`，`v = 0.5 - dot(P, Up)`。
  同一个角点在每个面上有独立 UV，因此仍然需要 24 顶点。
- **WIC 解码**：`Scene/Texture.cpp` 内部走
  `IWICImagingFactory → IWICBitmapDecoder → IWICBitmapFrameDecode →
   IWICFormatConverter(32bppRGBA) → CopyPixels`，得到 CPU 侧 RGBA8 像素。
- **上传 GPU**：`R8G8B8A8_UNORM`；当前使用
  `DEFAULT + RENDER_TARGET + GENERATE_MIPS`，上传 level 0 后 `GenerateMips`
  生成完整 mip 链；Sampler 使用 8× anisotropic filtering。详见 §6。
- **Gamma**：仍未做 sRGB 线性工作流，留作后续。
- **资源绑定**：`Material.TexturePtr` 非拥有地指向 `Scene::TextureA`（CubeA）或
  `Scene::TextureB`（CubeB）；Renderer 每个 DrawCall 绑定 `t0`（SRV）和
  `s0`（SamplerState），PS 用 `gTexture.Sample(gSampler, uv)` 采样。
  M11 又用 `Material.NormalTexturePtr` 绑定 `t3`（见 §2.18）。
- **第二张颜色贴图**：`Scene::TextureB` 加载 `img_cube_2.JPG`，给半透明 CubeB；
  与 TextureA 共用 WIC + GPU GenerateMips 路径，失败时独立生成棋盘格 fallback。
- **默认纹理**：不贴图的材质（地面）指向 `Scene::DefaultWhite`（1×1 白色），
  这样 shader 不需要“有没有贴图”的分支。
- **Fallback**：`img_cube.JPG` / `img_cube_2.JPG` 缺失或解码失败时，
  `Texture::CreateCheckerboard` 生成棋盘格，程序继续运行，贴图链路仍可验证。
- **COM 生命周期**：WIC 是 COM 组件；`DemoMain` 用 `ComScope` RAII 初始化/反初始化，
  且 `Scene` 比 `ComScope` 先析构，确保 WIC 对象在 `CoUninitialize` 前释放。

### 2.11 M6 半透明 Pass

- **分流**：Renderer 收集可渲染物时按 `MaterialData.bIsTransparent` 分成
  `opaqueActors` / `transparentActors` 两个列表（≈ BasePass / Translucency Pass）。
- **排序**：半透明列表按 Actor 原点到相机的距离平方**从远到近**排序（画家算法）。
  逐物体排序对互不穿插的简单物体够用；互相穿插时仍会出错，彻底解决需要逐三角形排序或 OIT。
- **Opaque Pass**：`m_blendOpaque`（关闭混合）+ `m_depthOpaque`（深度测试 + 写深度）。
  不透明物体顺序无所谓，深度测试会兜底。
- **Translucency Pass**：`m_blendAlpha`（`SrcAlpha / InvSrcAlpha`）+
  `m_depthTransparent`（深度测试开启，`DepthWriteMask = ZERO`）。
  深度测试保证被不透明物遮挡的像素不画；不写深度保证后面的透明物仍然能混合。
- **透明立方体**：`BuildScene` 里 CubeB 使用 `Scene::TextureB`（`img_cube_2.JPG`），
  `BaseColor = (1,0.12,0.12,0.5)`、`TintStrength = 0.3`；
  PS 用 `lerp(texel.rgb, texel.rgb * BaseColor.rgb, TintStrength)` 做轻染色，
  因此贴图颜色为主、红色只作为染色倾向；Alpha 仍由 `BaseColor.a` 控制。
  位置略抬高并放在 CubeA 与相机之间，便于观察“透过 B 看到 A”。
- **自遮挡**：透明 Pass 仍使用 CULL_BACK，只画朝向相机的面，避免同一个立方体的正面/背面
  互相覆盖；如果要看到玻璃内壁，需要在物体内部做逐三角形排序。

### 2.12 M7 阴影：Shadow Map（已实现）

> 目标：所有不透明物体都能把阴影投到接收面上；半透明 CubeB 不投实心阴影。
>
> 实现：`RHI/RenderTarget`（depth-only）+ `Renderer/ShadowMap` + `shaders/Shadow.hlsl`；
> 主 shader 通过 `t1/s1/b2` 采样 ShadowMap。

- **两个 Pass**：
  1. **Shadow Pass（光视角）**：用正交光源相机渲染所有 caster 的深度到 ShadowMap；
  2. **主 Pass（相机视角）**：把世界坐标变换到光源裁剪空间，和 ShadowMap 比较深度。
- **平行光相机**：当前 `DirectionalLight::Direction` 是“表面 → 光源”的 L，所以
  `eye = sceneCenter + L * distance`，`LookAtLH(eye, center, up)` + `OrthographicLH`。
  平行光不能用透视投影，否则阴影比例会错。
- **ShadowMap 资源**：使用 depth-only `RenderTarget`（`R32_TYPELESS` 纹理，
  DSV 用 `D32_FLOAT`，SRV 用 `R32_FLOAT`），默认 2048×2048。
- **主 Pass 采样**：
  `lightClip = LightViewProj * worldPos`，除以 w 得到 NDC；
  UV 的 y 需要翻转（D3D 纹理 v=0 在顶部），深度用 D3D 的 [0,1] 区间比较。
- **PCF**：3×3 比较平均，柔化边缘；深度采样用点采样，避免“先线性平均深度再比较”。
- **Bias**：光栅化阶段使用 slope-scaled depth bias，shader 里再加一个按 N·L 调整的
  depth bias，权衡 acne（条纹）和 peter-panning（阴影脱离物体）。
- **投射/接收策略**：
  - `StaticMeshActor::bCastShadow` 默认 `true`；
  - 地面建议 `bCastShadow = false`，只接收，避免无意义的自阴影 acne；
  - 半透明 CubeB 不进入 Shadow Pass；它仍然可以接收阴影。
- **只影响直接光照**：`color = ambient + (diffuse + specular) * shadow`，
  环境光不乘 shadow，避免阴影纯黑。
- **实现落点**：`ShadowMap` 固定 2048×2048、正交范围 20×20、光源距离 20；
  `RenderTarget` 负责 depth-only 资源；`ShaderSet::LoadVSFromFile` 编译 Shadow VS；
  主 Pass 绑定 `t1`（ShadowMap）、`s1`（点采样器）、`b2`（`ShadowCB`）。
- **场景配置**：`StaticMeshActor::bCastShadow` 默认 `true`；地面设为 `false`，
  只接收不投射；透明 CubeB 不进入 Shadow Pass。为了让默认机位能看到阴影，
  CubeB 放在 CubeA 左侧，CubeA 的阴影落在右后方地面。
- **D3D11 注意点**：ShadowMap 作为 DSV 渲染前要先从 SRV 槽解绑；Shadow Pass 结束后
  必须恢复主视口（`ClearBackBuffer` 负责重设）。

### 2.13 渲染目标与 Pass 框架（M8+ 设计）

> 目标：为后处理、MRT/G-Buffer、平面镜预留统一的离屏 RT 和全屏 Pass 框架；
> 不引入完整 Render Graph，保持代码可读。

- **概念区分**：
  - MRT：一次 DrawCall 写多张颜色纹理（G-Buffer、法线/材质/速度）；
  - 离屏 RT：一个 Pass 渲染到纹理，另一个 Pass 采样（后处理、镜面、ShadowMap）。
  镜面和后处理主要需要离屏 RT，不一定需要 MRT。
- **UE 对照**：
  - RHI：`FRHITexture / FRHIRenderTargetView / FRHIDepthStencilView / FRHIShaderResourceView`；
  - RDG：`FRDGBuilder / FRDGTextureRef / AddPass / FRDGRenderTargetBinding`，负责依赖、
    生命周期、跨 API 屏障和临时资源别名；
  - `FSceneTextures` 统一管理 SceneColor / SceneDepth / G-Buffer 等场景纹理；
  - 后处理、平面反射都是图中的 Pass；本 demo 不复制完整 RDG。
- **本 demo 的最小抽象（当前状态）**：
  - `RHI/RenderTarget`（已实现）：单张颜色/深度/深度-only RT，拥有 Texture/RTV/SRV/DSV、
    `Create/Resize/Clear/Bind`；
  - `RHI/RenderTargetGroup`（已实现，暂未使用）：多张颜色 RTV + 一个共享 DSV，
    为 MRT/G-Buffer 预留；
  - `Renderer/FullscreenPass`（已实现）：`SV_VertexID` 全屏三角形 + PS 采样；
  - `Renderer/PostProcess`（已实现，LDR 多模式）：SceneColor + 全屏拷贝/灰度/暗化蒙版；
  - `Renderer/PlanarMirror`（已实现）：镜像相机 + Reflection RT + 镜面采样；
    当前未做裁剪面/递归反射；
  - `Renderer` 按显式顺序组织 Pass，不实现依赖图和资源别名。
- **计划阶段**：
  1. M7（已完成）：`RenderTarget` 先服务 ShadowMap；
  2. M8（已完成）：SceneColor 离屏渲染 + 灰度/暗角后处理；
     M8.5（已完成）：Stencil 蒙版 + 暗化后处理（数字键 3 循环模式）；
  3. M9：MRT/G-Buffer debug（按需求跳过）；
  4. M10（已完成）：平面镜反射（镜像相机、Reflection RT、绕序翻转）；
  5. 之后可选 HDR + Tonemap + Ping-pong Bloom / RenderTargetPool。
- **格式建议**：SceneColor 先用 `R8G8B8A8_UNORM`，后续 HDR 用 `R16G16B16A16_FLOAT`；
  深度 SRV 用 typeless 纹理（`R32_TYPELESS` + DSV `D32_FLOAT` + SRV `R32_FLOAT`）；
  G-Buffer 法线用 `R16G16B16A16_FLOAT` 或 `R10G10B10A2_UNORM`。
- **关键坑**：同一纹理不能同时作为 SRV 和 RTV/DSV 绑定；Resize 时重建屏幕尺寸 RT；
  离屏 Pass 后恢复主视口；镜面反射要翻转绕序并做裁剪面；MRT + MSAA 需要 resolve。

### 2.14 M8 / M8.5 后处理实现

- **SceneColor RT**：`R8G8B8A8_UNORM` 颜色 + `D24_UNORM_S8_UINT` 深度，
  由 `PostProcess::Initialize` 创建；窗口 Resize 时 `OnResize` 重建。
- **主场景流程**：
  `ShadowMap → PostProcess::BeginScene（绑定 SceneColor）→ Opaque/Translucent → EndScene`。
  主场景不再直接写后台缓冲。
- **全屏 Pass**：
  - `FullscreenPass` 用 `SV_VertexID` 生成覆盖屏幕的三角形，不需要 VB/IB；
  - `ShaderSet::LoadFullscreenFromFile` 编译 VS/PS，不创建输入布局；
  - PS 拆成三个入口：`CopyPS` / `GrayscalePS` / `MaskedDarkenPS`；
    `PostProcess` 按模式绑定不同的 `FullscreenPass`，避免 shader 内 uniform branch。
  - 三个变体目前各自持有一份 VS/Sampler，启动时重复编译 VS；
    规模小可接受；真实引擎会共享 VS/PSO，并用 shader cache 管理 permutation。
- **状态隔离**：后处理必须显式绑定自己的 BlendState（关闭混合）、
  DepthStencilState（关闭深度）、RasterizerState（实体 + CULL_NONE）；
  不能继承主 Pass 的半透明混合、线框或深度状态。
- **资源绑定**：EndScene 绑定后台 RTV 后再采样 SceneColor；SceneColor 的 SRV
  在下一帧绑定 RTV 前必须解绑。
- **模式循环**：数字键 3 循环 `Off → Grayscale → MaskedDarken → Off`；
  1/2 已用于相机切换，所以后处理使用 3。控制台会打印当前模式。
- **当前范围**：LDR、灰度/暗角和 Stencil 蒙版暗化；HDR/Tonemap/Bloom/Ping-pong 留到后续。

### 2.15 M8.5 Stencil 蒙版后处理

> 目标：场景整体接近纯黑，但 CubeB 覆盖的屏幕区域保持后处理前的原色。

- **模板来源**：SceneColor 的深度格式是 `D24_UNORM_S8_UINT`，自带 8 位 stencil；
  `PostProcess::BeginScene` 清屏时把 stencil 清成 0。
- **写模板**：`StaticMeshActor::bWriteStencil` 默认 `false`，CubeB 设为 `true`。
  透明 Pass 对 CubeB 使用 `m_depthTransparentStencil`：
  `StencilFunc = ALWAYS`、`StencilPassOp = REPLACE`、`StencilRef = 1`、
  `StencilDepthFailOp = KEEP`；深度测试仍然开启，所以只有可见片元写入。
- **后处理两个 Pass**：
  1. **Copy Pass**：把 SceneColor 原样拷贝到后台缓冲（`gParams.x=0`）；
  2. **MaskedDarken Pass**：绑定后台 RTV + SceneColor DSV，使用
     `CompareFunc = NOT_EQUAL`、`StencilRef = 1`、所有 StencilOp = KEEP、
     `StencilWriteMask = 0`；只在 stencil != 1 的像素压暗。
- **为什么需要 Copy Pass**：模板测试只能屏蔽写入，不能恢复原色；如果只做
  MaskedDarken Pass，CubeB 区域会保留后台缓冲的旧内容，而不是当前帧 SceneColor。
- **压暗公式**：`color = scene.rgb * 0.35 + darkTint`，其中
  `darkTint ≈ (0.008, 0.010, 0.016)`；保留极少量冷色底，避免暗部完全死黑。
- **状态隔离**：Copy Pass 使用深度/模板都关闭的状态；MaskedDarken Pass 使用
  深度关闭、模板开启的状态。两者都使用后处理自己的 Blend/RasterizerState。

### 2.16 M10 平面镜反射

> 目标：在场景右侧放一面竖直镜面，反射出 CubeA 的背面/侧面和地面阴影，
> 镜面本身是淡白色并与反射 RT 混合。

- **镜面几何**：`Mesh::CreateVerticalPlane` 生成局部 XY 平面（法线 +Z），
  Actor 通过 yaw 旋转到朝向 CubeA 的方向；底部落在地面 y=-0.5。
- **镜像相机**：不是简单“把相机放到镜子后面”，而是把主相机关于镜面平面做反射。
  行向量约定下，仿射反射矩阵为：
  `p' = p - 2(n·p + d)n`，3x3 部分是 `I - 2nn^T`，平移放在第 4 行。
  然后 `mirrorViewProj = R * mainView * mainProj`。
- **绕序翻转**：反射矩阵行列式为负，三角形绕序翻转；反射 Pass 使用
  `CULL_FRONT` 的 RasterizerState（线框模式仍用 CULL_NONE）。
- **Reflection RT**：颜色 `R8G8B8A8_UNORM` + 深度 `D24_UNORM_S8_UINT`，
  与主窗口同尺寸；`PlanarMirror::OnResize` 负责重建。
- **Pass 顺序**：
  1. ShadowMap（光源）；
  2. Reflection Pass：镜像相机 → Reflection RT，跳过镜面自身；
  3. 主 SceneColor Pass：Opaque（包含镜面）/ Translucent；
  4. 后处理 → 后台缓冲。
- **镜面 Shader**：VS 用主相机 `ViewProj` 绘制镜面；PS 用镜像相机的
  `MirrorViewProj` 把世界坐标换算成反射纹理 UV（y 翻转），
  采样 Reflection RT 后与 `MirrorTint`（淡白色）做 lerp。
- **M10 的取舍**：
  - 镜面自身不投影（`bCastShadow=false`），不写 stencil；
  - 反射 Pass 不渲染镜面，避免反馈/递归；
  - 当前没有斜近裁剪面（场景中镜面后方没有其它物体），也没有递归镜面；
  - 反射 Pass 包含正常光照和 ShadowMap，因此镜中能看到 CubeA 背面与阴影；
    镜面表面本身没有额外的平行光高光，只有反射 + 淡白色 tint。
- **SRV/RTV 解绑**：镜面 PS 从 `t2` 采样 Reflection RT；画完镜面后立即解绑 `t2`。
  下一帧 Reflection RT 作为 RTV 之前还会统一清空 PS 输入槽，避免同一资源同时
  作为输入和输出（详见 §4 第 14 条）。
- **RT 归类**：SceneColor、ReflectionColor、ShadowMap 以及 M10.5 的 FXAA Target
  是多个离屏 RT，但不是同时写多张颜色附件的 MRT；M9 的 `RenderTargetGroup` 仍未启用。

### 2.17 M10.5 FXAA

> 目标：用最小的管线改动减轻几何边缘锯齿，并保留数字键 0 独立开关。

- **Pass 顺序**：
  `SceneColor →（FXAA）→ FXAA Target → Copy/Grayscale/MaskedDarken → 后台缓冲`。
  FXAA 在颜色后处理之前执行，避免把 Stencil 蒙版的边界一起模糊。
- **FXAA Target**：`R8G8B8A8_UNORM` 颜色 RT，不需要深度；与窗口同尺寸，
  由 `PostProcess::OnResize` 重建。因为不能同时读写同一张纹理，FXAA 必须经过这张 RT。
- **Shader**：`FXAA.hlsl` 的 `FXAAPSMain`：
  - 采样中心 + 四个对角邻居的亮度；
  - 局部亮度范围低于阈值时直接返回原色；
  - 用亮度梯度估计边缘方向，沿边缘方向采样两组颜色；
  - 选择不超出局部亮度范围的混合结果。
- **开关**：数字键 0 独立控制 `m_fxaaEnabled`；默认关闭。
- **兼容性**：MaskedDarken 的颜色源可以来自 FXAA Target，但模板仍读取
  SceneColor 的 stencil；FXAA 不会改变 CubeB 的蒙版区域判定。
- **当前限制**：FXAA 会让画面略微变软；Reflection RT 本身没有单独做 FXAA，
  镜中反射边缘仍可能有锯齿；没有 MSAA/SSAA。
- **边界**：FXAA 只处理屏幕空间亮度边缘，不能解决纹理 minification / 掠射角
  采样不足导致的图案闪烁；后者由 M10.6 的 mipmap + anisotropic filtering 处理（见 §6）。

### 2.18 M11 切线空间法线贴图

> 目标：让 CubeA 在原有颜色贴图之外使用 `normal_tian.png`，通过 TBN 把切线空间法线
> 变换到世界空间，参与 Lambert 与 Blinn-Phong 光照；法线贴图必须是独立资产，
> 不在 `DemoMain` 或运行时程序化生成。

- **资产**：`assets/normal_tian.png`，512×512；由
  `tools/generate_tian_normal.ps1` 离线生成。高度场包含四块平坦高台、中央“田”字凹槽、
  凹槽倒角和外边缘倒角。生成器把高度场中心差分编码成切线空间法线。
- **顶点扩展**：`Vertex` 从 `Position/Normal/UV` 扩展为
  `Position/Normal/Tangent/Bitangent/UV`；输入布局新增 `TANGENT/BITANGENT`，
  仍用 `offsetof` 计算偏移。阴影 VS 和镜面 VS 只声明 `POSITION`，但顶点缓冲 stride
  统一使用 `sizeof(Vertex)`。
- **切线基**：
  - 立方体：`Right = normalize(cross(Normal, Up))`，`u = dot(P, Right) + 0.5`，
    `v = 0.5 - dot(P, Up)`；所以 `T = Right`、`B = -Up = dP/dv`；
  - 地面：`T = +X`、`B = -Z`，对应 `u = x`、`v = -z`；
  - 竖直镜面：填充 `T = +X`、`B = -Y`，但 Mirror shader 只使用位置，不参与法线映射。
- **VS 变换**：几何法线用 `gNormalMatrix`（世界矩阵逆转置）变换；
  `Tangent/Bitangent` 是切向方向，用 `gWorld` 变换。PS 插值后对 T/B 做 Gram-Schmidt
  正交化，避免非均匀缩放或插值造成基不垂直。
- **PS 采样**：
  ```hlsl
  float3 T = normalize(input.tangent - N * dot(N, input.tangent));
  float3 B = normalize(input.bitangent - N * dot(N, input.bitangent)
                       - T * dot(T, input.bitangent));
  float3 tangentNormal = gNormalMap.Sample(gSampler, input.uv).xyz * 2.0f - 1.0f;
  N = normalize(T * tangentNormal.x + B * tangentNormal.y + N * tangentNormal.z);
  ```
  之后 `N` 统一用于 `N·L`、`N·H` 与阴影 bias。默认平坦法线解码后约等于 `(0,0,1)`，
  因此同一个 shader 可以无条件采样，不需要“是否有法线贴图”的分支。
- **资源约定**：`Material.NormalTexturePtr` 非拥有地指向 `Scene::NormalTexture` 或
  `Scene::DefaultNormal`；`Renderer::DrawObject` 每个 DrawCall 绑定 `t3`，与颜色贴图
  共用 `s0`。`DefaultNormal` 是 1×1 的 `(128,128,255)`，对应平坦法线 `(0,0,1)`。
  CubeA 使用 `normal_tian.png`；地面和 CubeB 使用 `DefaultNormal`。
- **通道约定**：贴图的 R = +U、G = +V、B = +N；生成器采用纹理 v 向下，且
  顶点 `B = dP/dv`。因此高度场法线为
  `(-dH/du, -dH/dv, 1)`，生成脚本里的绿色分量必须写成
  `ny = hUp - hDown`。如果导入外部 OpenGL 风格法线贴图，通常需要翻转 G。
- **视觉结果**：CubeA 的每个面使用同一张“田”字法线图；平坦象限基本只受几何法线影响，
  凹槽倒角在光照下出现明暗变化，高光会沿倒角形成细亮线。因为法线贴图与颜色贴图
  共用 UV，图案方向与人物肖像一致。
- **当前限制**：
  - 只有 CubeA 使用法线贴图；地面/CubeB 是平坦法线；
  - 法线图是 8-bit RGBA，尚未改为 BC5（只存 XY，Z 重建）；
  - 没有法线强度参数或运行时开关；调强度需要改生成器的 `normalStrength` 并重新导出；
  - 没有视差贴图/位移贴图，凹槽只是光照层面的凹凸，不改变轮廓。

## 2.19 M12 资产管理层（AssetManager）

> 目标：把"共享网格/纹理"从 Scene 的命名成员改为统一的资产注册表，
> 让 Scene（≈ UWorld）不再持有内容资产——这是 M5 以来最大的结构性偏离修复。

- **背景**：M5 引入贴图后，Scene 以 `TextureA / TextureB / CubeMesh / DefaultWhite ...`
  命名成员持有资产。场景类被迫认识 demo 的具体内容，加一张贴图要改
  Scene.h、Scene::Initialize、BuildScene 三处；UE 中 UWorld 从不拥有内容资产，
  资产由包系统 / UAssetManager 管理，Actor/Component 只持有引用。
- **方案**：`Scene/AssetManager`（与 Mesh/Texture 同层），名字键控注册表：
  - `unordered_map<wstring, Mesh/Texture>` 节点存储，元素地址在 rehash 后仍稳定，
    外发裸指针在"不删元素"前提下安全（本 demo 不删）；
  - **命名约定**（对照 UE 的 /Game 与 /Engine）：文件纹理用**相对路径**作名
    （`assets/img_cube.JPG`）；程序生成资产用虚拟路径（`Procedural/Cube`）；
    引擎内置资产用 `Engine/...`（`AssetName::DefaultWhite / DefaultNormal`，
    ≈ Engine Content 的默认纹理）；
  - **fallback 下沉**：`LoadTexture(name, path, ETextureFallback)` 内部处理失败兜底
    （颜色贴图 → 棋盘格；法线贴图 → 1×1 平坦法线），并以同名注册，契约是
    "返回非空 → 该名字必然可取到有效纹理"，调用方无需再判空；
  - 刻意不做：异步加载、软引用、句柄/ID、资产卸载。
- **结构变化**：
  - `Scene` 删除 8 个资产成员；`Scene::Initialize()` 只剩默认相机绑定；
  - DemoMain 新增 `LoadContent()` 步骤（≈ 引擎启动期 content loading），
    与 `BuildScene()`（场景摆放）职责分离：注册/加载 → 摆放；
  - `g_assets` 是匿名命名空间全局对象，**声明在 `g_scene` 之前**——逆序析构时
    Actor 先销毁，其持有的资产裸指针随后才随 AssetManager 失效（与 g_com 同理）；
  - 延续"显式传依赖"风格，不用单例；材质里仍是裸指针，Renderer 无需改动。
- **顺带修正**：Renderer.cpp 原来经由 Scene.h 间接包含 Texture.h，
  现在按"用谁包含谁"显式包含；BuildScene 两处过时注释（地面颜色、
  CubeB 的 TintStrength/alpha 数值）与实际代码对齐。

## 2.20 M13 点光源（前向多光源）

> 目标：用最简单可配置的点光源参数，验证前向渲染的多光源流程。
> 关键认知：**光源数量与材质/shader 映射正交**——光照是帧级环境数据，
> 材质是物体级表面数据，加灯不需要新增 shader 变体。

- **数据**：`Scene/Light.h` 新增 `PointLight { Position, Range, Color(rgb+a=强度) }`；
  `Scene` 持有 `std::array<PointLight, kMaxPointLights> PointLights` + `NumPointLights`
  （≈ FScene::Lights 数组的最小版）。上限 4，与 CB/HLSL 数组大小一致。
- **UE 对照**：UE 的材质 permutation 由材质特性（shading model、blend mode）驱动，
  从不由灯的数量驱动；前向多光源靠帧级光源列表解决（UE 是 clustered shading 的
  light list，本 demo 是 CB 数组 + 动态循环）。真正需要"材质→shader 映射"的时刻是
  出现不走标准光照的材质（如镜面，目前靠 `bIsMirror` 特判）或按物体筛选光照
  （light channels），点光源两者都不是。
- **CB 布局**：`PerFrameCB` 扩展 `PointLightCB[4]`（每个点光两个 float4：
  `(pos.xyz, range)` + `(rgb, 强度)`，天然满足 HLSL 数组 16 字节元素对齐）+
  `LightCounts.x`（生效数量）。`UpdatePerFrameConstants` 改为接收 `const Scene&`，
  未启用槽位保持全零（强度 0 即无贡献），数量用 `std::clamp` 限制在 [0, 上限]。
  Mirror.hlsl 只声明 `gViewProj` 前缀字段，cbuffer 扩展对前缀偏移无影响。
- **Shader**：`Cube.hlsl` 在方向光计算之后循环点光源——
  衰减 = `saturate(1 - d/range)²`（范围平滑截断）× `1/(1+d²)`（防零距离爆亮），
  漫反射/高光复用现有 Lambert + Blinn-Phong；最终
  `color = ambient + (diffuse + specular)·shadow + pointSum`，
  点光源贡献不受平行光 shadow 影响。
- **阴影策略**：点光源不投阴影。点光阴影需要 cubemap + 6 个 Pass，
  是另一个量级的里程碑。
- **反射 Pass 零成本继承**：镜像相机 Pass 用同一个 shader、同一条
  `UpdatePerFrameConstants` 路径，镜中自动带点光源光照。
- **配置入口**：`BuildScene` 末尾；当前两盏——暖橙在 CubeA 右前方（范围 5、
  强度 3），冷蓝在左后方（范围 6、强度 2.5），地面上可见两片不同颜色的光斑。
- **限制**：衰减为教学近似（非物理光度单位）；固定上限 4；无光源可视化
  （unlit 材质属于第二种 shader 路径，暂缓）；光源无 Tick/动画。
- **排错记录**：旧版 HLSL 编译器（fxc 10.1 / D3DCompiler_47）**不支持
  `static_cast<int>(x)`**，应使用 C 风格 `(int)x`。shader 是运行时编译，
  构建期不检查，可用 SDK 自带 fxc 离线验证：
  `fxc /T ps_5_0 /E PSMain shaders/Cube.hlsl`。

## 2.21 M14 光源 Actor 化

> 目标：把光源从 Scene 的命名成员改为 Actor 层级（≈ UE 的
> `ALight → ADirectionalLight / APointLight`），Scene 不再特殊持有光源。

- **层级**（`Scene/Light.h/.cpp`）：
  - `LightActor : Actor`：共享参数 `Color`（rgb = 光色，a = 强度）；
  - `DirectionalLightActor`：`Ambient`（环境光）+ 方向由 **Actor Rotation** 决定
    （≈ UE 平行光用朝向表达方向）；Location/Scale 无意义；
  - `PointLightActor`：`Range`（影响半径）；位置直接用 **Actor::Location**；
  - 光源默认无行为（基类 Tick 空实现）；以后想加环绕/闪烁，override Tick 即可。
- **Scene**：删除 `Light` / `PointLights` 成员。光源由 `SpawnActor` 纳入统一管理，
  渲染收集时与 StaticMeshActor 走同一条遍历——这正是 UE 里
  "UWorld 不特殊对待光源，FScene 收集时识别 light" 的结构。
- **Renderer 收集**：dynamic_cast 三分支（StaticMesh / DirectionalLight /
  PointLight）。只支持一盏平行光（多余的忽略）；场景没有平行光时用函数级
  static 默认光兜底 + 一次性警告，保证 ShadowMap/常量上传不断链。
  `UpdatePerFrameConstants` 改为接收收集到的光源指针，不再接触 Scene。
- **平行光方向**：`GetLightDirection()` = 本地 +Z 经 `XMMatrixRotationRollPitchYaw`
  旋转后取反（L = -传播方向），下游 ShadowMap / shader 的 L 约定不变。
  配置等效角度 `(0.5893, 0.9153, 0)` ≈ 旧 `Direction = (-0.65, 0.55, -0.50)`。
- **shader / CB 布局零改动**：纯 CPU 侧数据来源重构，视觉与 M13 一致。
- **附带收益**：点光源位置/平行光方向现在用和网格实例同一套 Transform 语言表达；
  多光源"多放几个 Actor"即可，配置语义更清晰。
- **排错记录**：见 §4 第 26 条（Actor 与相机 pitch 符号约定相反）。

## 2.22 M15 光源位置指示器

> 目标：在光源位置画一个小方块方便定位——不透明、颜色 = 光源 Color、
> 无贴图、**本身不对光产生遮挡**。

- **指示器是渲染侧关切**（≈ UE 编辑器里的光源图标/精灵，而非游戏内物体）：
  `LightActor` 只带 `bShowIndicator` 开关和 `IndicatorSize`（默认 0.15m），
  不持有任何渲染资源；共用网格由 Renderer 通过 `SetLightIndicatorMesh`
  一次性持有（当前是 `Procedural/Cube`）。点光源默认开启；平行光默认关闭
  （位置对它无意义，但机制上也允许打开）。
- **"颜色与光源一致" ⇒ 必须 unlit**：走光照管线的话指示器颜色会被场景光
  污染（被平行光照亮、被阴影压暗）。这就是 §2.20 预言过的"第二种 shader
  路径"首次出现——但没有引入 shader 注册表：`shaders/Unlit.hlsl` 是一个
  极简专用 shader，复用现有 b0（gViewProj）/ b1（gWorld + gBaseColor）
  常量布局（前缀/占位声明），零新基础设施。
- **"不遮挡光"的三层落实**：
  1. 指示器不是 `StaticMeshActor`，永远不会进入 `shadowCasters` 列表
     → 不投阴影（关键）；
  2. 在 Opaque Pass 用 `m_depthOpaque` 绘制，stencil 关闭 → 不写蒙版；
  3. unlit、不参与光照 → 自身不接收光，也不需要被光"找到"。
  不透明深度正常：可以遮挡别的物体，也会被别的物体遮挡。
- **渲染收集**：`Renderer::Render` 在类型分支之外，额外对所有
  `LightActor` 收集 `indicatorLights` 列表；主 Pass 与反射 Pass 的
  Opaque 段末尾各调一次 `DrawLightIndicators`（镜中同样可见）。
- **颜色细节**：输出取光源 `Color.rgb`，alpha 固定 1；**强度不参与显示**——
  强度 >1（如暖橙的 3.0）乘进 RGB 会被 LDR 钳成白色，反而丢失颜色信息。
- **当前限制**：指示器形状固定为立方体（球/箭头形状是美术问题，不是机制问题）；
  强度/范围无可视化（范围球需要线框球体，留待以后）；平行光指示器只显示
  一个点，不表达方向（方向箭头需要按 Rotation 摆网格，目前指示器不旋转）。

## 2.23 M16 风格化渲染（Toon）

> 目标：新增 CubeC，验证"同一类对象上的第二种着色模型"——扁平的阶梯量化
> 着色 + 夸张的黑色描边。这是 §2.20 预言的"材质→shader 映射"落地时刻。

- **材质侧**：`EShadingModel { Lit, Toon }` 枚举落地（用枚举而不是 ShaderSet*，
  保持 Scene 不依赖 Renderer 的模块方向）；描边颜色/宽度作为材质参数
  （Lit 材质忽略，每个 Material 多 16 字节）。
- **shader 资产**：`Toon.hlsl` 一个文件两对入口——本体 `VSMain/PSMain` +
  描边 `OutlineVSMain/OutlinePSMain`。这就是"多 Pass 在 shader 资产内部"
  （≈ Unity 单 shader 多 Pass 的最小版）；`ShaderSet::LoadFromFile` 增加
  入口名重载，默认仍取 VSMain/PSMain。
- **本体 PS**：N·L 量化成 3 档（>0.6→1.0，>0.2→0.55，其余→0.18；背光面不给 0
  是 toon 的常见风格选择）；贴图/染色约定与 Lit 一致；阴影采样保留
  （band × 连续 shadow，想更硬可再 step）；点光源同一套衰减 + 同一套量化；
  无高光、不采样法线贴图。
- **描边（inverted hull）**：VS 把顶点沿世界空间法线外扩 `OutlineWidth`，
  `CULL_FRONT` 只画背面并输出纯色；先画描边再画本体，hull 在轮廓处探出
  形成黑边。两次 DrawIndexed 都在 Opaque Pass 内，深度正常参与。
- **反射 Pass 的绕序细节**：反射里绕序翻转，本体用 CULL_FRONT（反射光栅化
  状态），描边就必须换回 CULL_BACK——两个状态在反射 Pass 里互换角色，
  两个状态都是现成的，零新增。
- **与各系统交互**：
  - 阴影投射：走共享 Shadow VS（纯几何），CubeC 自动投影；hull 不在
    Shadow Pass → **描边不会让影子膨胀**（inverted hull 的天然优点）；
  - stencil/后处理/FXAA/半透明排序：零交互；
  - 线框模式：两个 Pass 都切换为线框状态。
- **Renderer 分流**：`DrawObject` 在镜面特判之后按 `ShadingModel` 分流到
  `DrawToonObject`（CB/IA/贴图绑定与 Lit 共用前置代码）。
- **已知限制**：
  - 世界空间等宽描边（近粗远细）；屏幕空间等宽需要 clip 空间按 w 缩放，进阶；
  - 量化档位阈值写死在 shader 里（应做成材质参数？留给需要时）；
  - **硬边几何的角点裂缝**：24 顶点立方体每个角点有三份顶点（各带一个面
    法线），外扩时三个顶点朝三个方向移动，角点会裂开细缝（宽度 0.025 时
    约几厘米，风格化下可读作"破形"）。标准解法是存一份角点平均法线专供
    外扩（额外顶点属性或顶点色通道），本 demo 未做。

## 4. 排错记录（值得长期记住的）

1. **矩阵"双重转置"**：两种约定必须成对使用——`transpose 上传 + mul(v,M)`（行向量派）
   或 `直接上传 + mul(M,v)`（列向量派，HLSL 列主序自动转置）。混用导致 WVP·v，顶点 z 全部出界被裁。
2. **常量缓冲按着色阶段分别绑定**：PS 读的颜色忘了 `PSSetConstantBuffers` → 黑色立方体。
3. **同一面的两个三角形绕序必须一致**：+Z 面一个三角形绕反，转到该面朝相机时被误剔除出缺口。
4. **纯色封闭网格整体绕序翻转不可见**：轮廓/颜色/深度表现完全正常地渲染"内壁"。
   立方体从 M2 起整体朝内，直到加地面平面才暴露（平面破洞透出地面）。
   暴露手段：线框+剔除 / 多色 / 光照 / 穿模观察。
   **教训：手工填索引后先用右手定则抽查每面法线方向，别看轮廓"像对"就过。**
5. **截图验证也可能是假阳性**：实体与线框画的是同一批（远）面时，"两张图一致"≠"两张图都对"。
   （环境问题：175% DPI 缩放下逻辑/物理像素混用也曾导致截图误读。）
6. **法线不能直接用世界矩阵变换**：非均匀缩放会让法线不再垂直于表面，必须用世界矩阵的
   逆转置 `(World^-1)^T`。本 demo 在 CPU 端算好上传，shader 里用
   `mul((float3x3)gNormalMatrix, n)`；矩阵转置约定要和位置变换保持一致。
7. **平面上的 Blinn-Phong 高光近似均匀**：立方体每个面只有一个法线方向，高光不会形成
   球面那样的圆形亮斑；指数越大，整面高光越容易直接消失。想看明显高光需要球面或法线贴图。
8. **WIC 是 COM 组件**：`CoCreateInstance(CLSID_WICImagingFactory)` 之前必须初始化 COM，
   否则会得到 `CO_E_NOTINITIALIZED`。本 demo 在 `main` 里用 `ComScope` RAII 包住，
   并保证 `Scene` 先析构、`CoUninitialize` 后执行。
9. **WIC 输出格式要和 DXGI 格式配对**：`GUID_WICPixelFormat32bppRGBA` 对应
   `DXGI_FORMAT_R8G8B8A8_UNORM`；如果错配成 BGRA，最典型的现象是红蓝互换。
   另外 `CopyPixels` 的 stride 和 `D3D11_SUBRESOURCE_DATA::SysMemPitch` 都必须是
   `width * 4`，所以上传前要拿到转换后的宽高。
10. **UV 方向与 sRGB**：WIC 的像素行是从上到下的，D3D11 纹理坐标 `(0,0)` 也在左上角，
    因此不需要垂直翻转。当前贴图用 `UNORM` 采样，光照是在 sRGB 数值上近似计算；
    严格的线性工作流需要 `_SRGB` 纹理 + sRGB 后备缓冲，留作后续优化。
11. **半透明必须后画且不写深度**：透明物体要参与深度测试（被不透明物挡住时不画），
    但 `DepthWriteMask` 必须为 ZERO；否则它会写入深度，把它后面的其他透明物挡掉。
    同一帧内还要按相机距离从远到近排序，`SrcAlpha / InvSrcAlpha` 混合结果才正确。
    此外，透明物体仍建议 CULL_BACK，避免一个凸网格的正面/背面自混合顺序不确定。
12. **法线贴图有三套必须对齐的约定**：UV 的 +V 方向、顶点 `Bitangent` 的方向、
    高度场差分符号。本 demo 用 `B = dP/dv`，所以切线空间法线是
    `(-dH/du, -dH/dv, 1)`；如果绿色通道符号写反，凹槽会看起来像凸起，
    而且从单一角度的截图里不一定能立刻看出来。外部 OpenGL 法线贴图通常还要翻转 G。
13. **TBN 的 T/B 不能直接用法线矩阵**：`Tangent/Bitangent` 是切向方向，按世界矩阵
    变换；几何法线才用逆转置矩阵。PS 里再做一次 Gram-Schmidt，可消除插值/
    非均匀缩放导致的不正交；否则法线贴图会出现方向性扭曲。
14. **ShadowMap 的坐标空间容易搞反**：平行光要用正交相机，`eye = center + L * distance`
    （`L` 是表面 → 光源）；主 Pass 中 NDC 的 y 要翻转成纹理 v，D3D 的深度是 [0,1]。
    如果阴影上下颠倒或深浅相反，先检查这三处。
15. **Shadow Pass 是离屏 Pass**：渲染前把 ShadowMap 从 SRV 槽解绑，避免同一资源同时
    作为 DSV/SRV；Pass 结束后必须恢复主视口（本 demo 由 `ClearBackBuffer` 统一重设），
    否则主画面会被 2048 的 ShadowMap 视口缩放/裁剪。
16. **Bias 是阴影质量的核心参数**：太小会出现自阴影条纹（acne），太大阴影会脱离物体
    （peter-panning）。本 demo 用 slope-scaled rasterizer bias + shader 端 N·L 相关 bias，
    先保证阴影连接正确，再根据画面微调。
17. **全屏后处理不能继承主 Pass 状态**：主 Pass 最后绑定的是半透明 BlendState、
    透明 DepthStencilState，甚至可能是线框 RasterizerState；全屏 Pass 必须显式绑定
    关闭混合、关闭深度、实体 CULL_NONE 的状态，否则后处理会被混合/线框污染。
18. **离屏 RT 的 SRV/RTV 不能同时绑定**：SceneColor、FXAA Target、Reflection RT
    在渲染时作为 RTV，在 shader 中又作为 SRV 采样；同一个资源不能同时输入和输出。
    本 demo 在 `PlanarMirror::DrawMirror` 后立即解绑 t2，在
    `PostProcess::BeginScene`/`EndScene` 切换 RTV 前统一清空 t0~t3；
    否则 Debug Layer 会报告
    `DEVICE_OMSETRENDERTARGETS_HAZARD` / `DEVICE_PSSETSHADERRESOURCES_HAZARD`。
    D3D Runtime 会自动纠正冲突，但状态设置不干净，应该显式修复而不是忽略。
    工具函数见 `RHI/D3D11State.h`。
19. **Stencil 蒙版要“先写、后测、再拷贝”**：主 Pass 用 `ALWAYS/REPLACE` 把 CubeB 写成 1，
    且 `StencilDepthFailOp = KEEP`；后处理效果 Pass 用 `NOT_EQUAL 1`、`StencilWriteMask = 0`。
    如果没有 Copy Pass，stencil=1 的像素不会被效果写入，但也不会自动变成当前帧原色，
    而是保留后台缓冲旧内容。
20. **模板测试要绑定 SceneColor 的 DSV**：EndScene 绑定后台 RTV 时必须同时绑定
    `SceneColor.GetDSV()`；后处理不做深度测试，但模板测试需要主 Pass 写下的 stencil。
    当前 SceneColor 深度是 `D24_UNORM_S8_UINT`；若改成纯 `D32_FLOAT`，模板功能会失效。
21. **HLSL 的 if 不是“一律慢”**：真正贵的是 warp/wave 内的 divergent branch。
    uniform branch（整个 draw/pass 条件相同）通常很便宜。本 demo 为学习目的把后处理
    PS 拆成三个变体，由 CPU 绑定不同 shader；代价是变体数量、编译/PSO 切换开销。
    简单模式保留 uniform branch 也完全合理，是否特化应以实际测量为准。
22. **平面镜不是“把相机放到镜子后面”**：要把相机关于镜面平面做**镜像反射**，
    再渲染场景；反射矩阵的行列式为负，三角形绕序会翻转，反射 Pass 必须使用
    `CULL_FRONT`（或等价地切换 `FrontCounterClockwise`）。否则会看到内壁/空洞。
23. **`XMMatrixReflect` 的齐次矩阵不要直接乘进 View**：它包含额外的 w 项，
    直接做 `R * V * P` 会污染投影 w 分量，反射画面错位。本 demo 手写了
    行向量仿射反射矩阵：3x3 为 `I - 2nn^T`，平移放第 4 行，w 保持 1。
24. **镜面 UV / RT 对齐**：镜面 PS 用镜像相机的 `ViewProj` 把世界坐标换算成
    反射 RT 的 UV；镜面自身不要进入反射 Pass，否则会反馈/递归。当前没有斜近
    裁剪面，因为场景里镜面后方没有物体；以后加物体时需要补裁剪。
25. **FXAA 需要单独的 RT**：不能同时读 SceneColor 和写 SceneColor；流程必须是
    `SceneColor → FXAA Target → 颜色后处理`。FXAA 放在灰度/暗化之前，避免把
    Stencil 蒙版边界一起模糊；FXAA 只处理颜色，不改变 stencil。
26. **Actor 与相机的 pitch 符号约定相反**：`CameraViewInfo::GetForward` 里
    pitch 正值 = 抬头（+y）；而 `XMMatrixRotationRollPitchYaw` 旋转本地 +Z 时，
    Rotation.x 为正值会得到 -y（低头）。同一组 (pitch, yaw) 放进两套路径会得到
    俯仰相反的方向。M14 平行光方向用 Actor Rotation 表达，配置角度时以
    `GetLightDirection()` 的输出为准，不要直接抄相机的角度。

## 5. 抗锯齿方案（FXAA 已实现）

当前输出是 1280×720。**FXAA 已实现**（数字键 0 独立开关，见 §2.17），
用来减轻 CubeA、镜面和地面的斜边锯齿；MSAA / SSAA 仍未实现。

### 方案 A：MSAA（硬件多重采样）

- 最适合几何边缘；常用 4×。
- 当前流程是“离屏 SceneColor + 后处理”，所以不是只改交换链：
  1. SceneColor / SceneDepth 用 `SampleDesc.Count = 4` 创建；
  2. 场景渲染到 MSAA RT；
  3. `ResolveSubresource` 到一张非 MSAA、带 SRV 的 SceneColor；
  4. 后处理/镜面采样 resolve 后的纹理；
  5. 最终全屏 Pass 写后台缓冲。
- 代价：显存/带宽增加；Reflection RT 若也要 MSAA，需要同样 resolve。
- **与 Stencil 蒙版的冲突**：M8.5 的后处理模板测试读取 SceneColor 的 stencil；
  MSAA 的 stencil 是逐 sample 的，不能直接给非 MSAA 全屏 Pass 使用。
  需要额外的非 MSAA mask RT，或者暂时关闭 MaskedDarken 模式。
- 交换链本身不一定要 MSAA，因为最后一步是全屏后处理；但若以后直接画后台缓冲，可以开 MSAA。

### 方案 B：FXAA（后处理抗锯齿，已实现）

- 全屏 Pass：检测亮度边缘，沿边缘方向混合邻域颜色。
- 复用现有 `FullscreenPass` / `PostProcess` 框架，不需要改 RT 采样数。
- 优点：接入简单、成本低、对几何和着色边缘都有效；缺点：画面会略微变软，
  细线和文字容易糊。
- 建议顺序：SceneColor → FXAA → 灰度/暗化等后处理；这样 Stencil 蒙版边界不会被 FXAA 模糊。
- 对当前 Demo 来说，这是**代码改动最小**的方案。

### 方案 C：SSAA（超采样）

- 以 1.5×/2× 分辨率渲染 SceneColor，再在后处理中降采样。
- 概念最简单，质量好；代价是像素数 ×2.25/×4，显存和填充率压力大。
- 如果只是想快速观察效果，可以把窗口/RT 放大再缩回，但不适合长期方案。

### 建议

1. **FXAA 已完成**：复用 FullscreenPass，改动小，能缓解当前锯齿；
2. 如果重点是复习硬件抗锯齿，下一步做 MSAA 4×，同时处理 SceneColor 的 resolve 和
   Stencil 蒙版的非 MSAA mask；
3. 不建议当前阶段上 TAA：需要 jitter、历史缓冲、速度缓冲和重投影，复杂度高。

## 6. 纹理采样、走样与 mipmap（M10.6 已实现）

当前纹理配置：

```text
源文件        : assets/img_cube.JPG（500×500）
CPU 像素格式  : WIC → RGBA8
GPU 纹理      : R8G8B8A8_UNORM
MipLevels     : 0（GPU GenerateMips 生成完整链）
Usage         : DEFAULT
Sampler Filter: D3D11_FILTER_ANISOTROPIC
Anisotropy    : 8×
```

M10.6 之前是 `MipLevels=1 + IMMUTABLE + MIN_MAG_MIP_LINEAR`，
这解释了当时 CubeA 顶部在掠射角下出现的图案闪烁。

### 6.1 为什么顶部图案会闪

纹理采样时，GPU 会计算 UV 在屏幕空间的导数 `ddx(uv)` / `ddy(uv)`，
估计一个像素覆盖了多少 texel：

- 正对纹理时，一个像素覆盖的 texel 少，采样清晰；
- 视角接近与顶面平行时，UV 在屏幕纵向上被极度压缩，一个像素可能覆盖
  很多 texel，这是典型的 **minification（缩小）采样**；
- 如果没有 mipmap（M10.6 之前），GPU 仍然只采样 level 0 的 500×500 原图，
  于是“一个像素从很多 texel 里随机取几个”，产生高频闪烁/摩尔纹；
- 相机远离时，物体在屏幕上变小，也是 minification；没有 mip 时同样会闪。

这是 **纹理走样（texture aliasing）**，和 FXAA/MSAA 处理的几何边缘走样不是一回事：

- **MSAA** 处理几何 coverage；
- **FXAA** 处理屏幕空间亮度边缘；
- **mipmap + anisotropic filtering** 才处理纹理采样 footprint。

FXAA 可能让边缘稍微柔和，但不会消除顶面纹理本身的闪烁。

### 6.2 相机远离时贴图精度会变吗

- **源纹理仍然是 500×500**，不会自动变成低分辨率资源；
- 变的是 **采样 LOD**：当前有完整 mip 链，GPU 根据屏幕 footprint 选择更低的 mip；
- 如果没有 mipmap（旧实现），无论物体在屏幕上多小，都只采样 level 0，
  既容易闪，也更容易造成纹理 cache thrashing；
- mipmap 不是“把原图永久降分辨率”，而是一条链，近处仍用 level 0，
  远处用 level 1/2/3…；
- 颜色精度仍是 8-bit；mipmap 改变的是空间分辨率，不是颜色位深。

### 6.3 当前实现（M10.6）

1. **生成 mipmap 链（已实现）**
   - 纹理使用 `D3D11_USAGE_DEFAULT`、`MipLevels=0`、
     `BindFlags = SHADER_RESOURCE | RENDER_TARGET`、
     `MiscFlags = GENERATE_MIPS`；
   - `UpdateSubresource` level 0 → `CreateShaderResourceView` → `GenerateMips`；
   - 棋盘格 fallback 也走同一条 mip 生成路径；
   - 1×1 默认白纹理保持单级（没有生成 mip 的必要）；
   - 500×500 NPOT 可以正常生成 mip；mip 链约增加 33% 显存。
2. **各向异性过滤（已实现）**
   - `Filter = D3D11_FILTER_ANISOTROPIC`；
   - `MaxAnisotropy = 8`；
   - `AddressU/V/W = WRAP`，`MaxLOD = D3D11_FLOAT32_MAX`；
   - 各向异性会在被压缩的轴向上多采样，改善顶面/地面这种掠射角。
3. **没有采用 CPU/离线 mip**
   - CPU box filter 和离线 DDS 方案保留在 §6.5，作为后续可选路线。
4. **区分闪烁来源**
   - 如果是纹理图案在闪：mipmap + anisotropic；
   - 如果是边缘在闪：MSAA / FXAA；
   - 如果是高光/镜面反射在闪：需要调整 roughness、使用预滤波高光或
     更高级的 specular anti-aliasing；单纯 mipmap 不一定解决。

### 6.4 对当前代码的落点（已完成）

- `Scene/Texture.cpp`：`CreateTextureFromPixels` 在有 context 且尺寸 >1×1 时
  使用 `MipLevels=0`、`DEFAULT`、`RENDER_TARGET + SHADER_RESOURCE`、
  `GENERATE_MIPS`；上传 level 0 后 `GenerateMips`。
- `Texture::LoadFromFile` / `CreateCheckerboard` / `CreateSolidColor`
  都增加了 `ID3D11DeviceContext*` 参数；`Scene::Initialize` 也增加 context 参数。
- `Scene.cpp` 的 `TextureA`（`img_cube.JPG`）和 `TextureB`（`img_cube_2.JPG`）
  都走同一条 WIC + GPU mip 生成路径；`TextureB` 仅供半透明 CubeB 使用。
- `Renderer.cpp`：sampler 改为 `D3D11_FILTER_ANISOTROPIC`，`MaxAnisotropy = 8`。
- 这两项和 FXAA 不冲突：FXAA 管屏幕边缘，mipmap/aniso 管纹理采样。
- 后续如果做 MSAA，再单独处理 SceneColor resolve 和 Stencil mask。

### 6.5 mipmap 的三条实现路线

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **离线 DDS** | 用 DirectXTex `texconv` 把 PNG/JPG 转成带 mip 的 DDS | 资产管线清晰，可同时做 BC7 压缩 | 需要额外工具；项目还要 DDS 加载器/DirectXTex 依赖 |
| **CPU 生成 mip** | WIC 解码后自己用 box filter 生成 mip 链，仍然上传 PNG/JPG | 不引入 DDS/第三方库，不需要 device context；保留 `IMMUTABLE` | 需要几十行像素处理代码；过滤质量是简单 box |
| **GPU GenerateMips** | 纹理改为 `DEFAULT` + `GENERATE_MIPS`，上传 level 0 后调用 `GenerateMips` | 代码最少，硬件过滤，不需要 DDS | 需要把 context 传进纹理加载；纹理不能再用 `IMMUTABLE` |

`texconv` 的典型离线命令（需要先拿到 DirectXTex 工具）：

```bat
texconv -f BC7_UNORM -m 0 -y -o assets assets\img_cube.JPG
```

- `-m 0`：生成完整 mip 链；
- `-f`：输出格式，学习期也可以先用 `R8G8B8A8_UNORM`；
- 生成的是 `.dds`，当前 WIC 加载器不能直接读，需要再加 DDS 加载路径。
- 如果只是想让当前 Demo 尽快消除闪烁，**GPU GenerateMips 最省事**；
  如果想顺便学习 BC7/资产压缩，再考虑 `texconv` + DDS。

**未来资产管线方向（保留设计）**：

```text
assets 只保留 .dds
    ↑ 导入时离线转换
PNG / JPG
    → texconv -m 0（生成 mip；可选 BC7 / sRGB）
    → DDS
    → 运行时 DDS loader / DirectXTex
```

这样可以把 mip 生成、BC7 压缩、sRGB 标记都放到导入阶段，
运行时只负责读 DDS，不再依赖 WIC。当前仍保留 PNG/JPG + WIC + GPU mip，
作为学习/开发期的轻量路径。

### 6.6 当前状态与后续

当前已采用：

```text
PNG/JPG（保留）
  → WIC 解码
  → GPU GenerateMips
  → Anisotropic Sampler（8×）
```

后续可选：

### 6.7 “田”字法线贴图资产（M11 已接入）

M11 使用了一个独立的“田”字法线贴图资产：

```text
tools/generate_tian_normal.ps1  →  assets/normal_tian.png
```

- 生成器是开发期 PowerShell 脚本，**不参与 DemoMain 运行时**；
- 输出是普通 PNG 纹理，和 `img_cube.JPG` 一样由构建后复制到输出目录；
- 高度场设计：
  - 四个象限是平坦高台；
  - 中间横竖两条“田”字线是凹槽；
  - 凹槽两侧和外边缘都有平滑倒角；
- 用高度场中心差分生成切线空间法线，编码到 RGB；
- CubeA 在 `Material.NormalTexturePtr` 中引用它，`Cube.hlsl` 通过 `t3/s0`
  采样并做 TBN 变换（详见 §2.18）。

注意：

- 生成器采用“纹理 v 向下”的约定，顶点 `Bitangent = dP/dv`；切线空间法线按
  `(-dH/du, -dH/dv, 1)` 计算，所以生成脚本的绿色分量是 `hUp - hDown`。
  外部法线贴图导入时要注意 DirectX / OpenGL 的绿色通道差异，必要时翻转 G；
- 如果未来统一走 DDS，法线贴图更常见的是 BC5（只存 XY，Z 重建）
  或无压缩 RGBA；不要随便用低质量 BC1；
- 当前法线图参与 GPU `GenerateMips` 和 8× anisotropic 采样；如果发现法线细节在
  远处被过度平均，可以在生成阶段限制 mip 数，或在 shader 里重新归一化。
